# 下次一定 V1.0 数据库设计文档

> 文档版本：V1.0  
> 产品版本：V1.0 MVP  
> 产品名称：下次一定 / For Next Time  
> 数据库：MySQL 8.x  
> 存储引擎：InnoDB  
> 字符集：utf8mb4  
> 排序规则：utf8mb4_0900_ai_ci  
> 文档状态：数据库设计评审稿  
> 设计依据：《下次一定 V1.0 产品需求文档》《下次一定 V1.0 系统设计文档》

---

## 1. 设计目标

数据库只服务于 V1.0 核心闭环：

```text
注册 / 登录
→ 留下一条内容
→ 分类 / 标签 / 备注
→ 搜索
→ 找到
→ 复制使用
```

设计原则：

- 表尽量少
- 字段含义清晰
- 用户数据严格隔离
- 支持逻辑删除
- 支持多标签
- 支持关键词搜索
- 支持置顶
- 支持复制次数和最近使用
- 不为 AI、OCR、社区等未来功能提前建表

## 2. 数据库名称

建议：

```text
for_next_time
```

本地创建示例：

```sql
CREATE DATABASE IF NOT EXISTS for_next_time
DEFAULT CHARACTER SET utf8mb4
```

## 5. 分类设计

V1 分类固定为：

| code | 中文 |
|---|---|
| `FUNNY` | 搞笑 |
| `ABSTRACT` | 抽象 |
| `EMOTION` | 感情 |
| `LITERARY` | 文艺 |
| `HEALING` | 治愈 |
| `SOBER` | 清醒 |
| `SARCASM` | 阴阳 |
| `OTHER` | 其他 |

数据库直接保存：

```text
content.category_code
```

不创建 category 表。

内容允许“不分类”，因此：

```text
category_code = NULL
```

`NULL` 与 `OTHER` 含义不同：

```text
NULL  = 没有选择分类
OTHER = 明确选择“其他”
```

## 6. 用户表 user_account

### 6.1 字段

| 字段 | 类型 | NULL | 默认 | 说明 |
|---|---|:---:|---|---|
| `id` | BIGINT UNSIGNED | 否 | AUTO_INCREMENT | 用户ID |
| `username` | VARCHAR(50) | 否 | - | 登录用户名 |
| `password_hash` | VARCHAR(100) | 否 | - | BCrypt 密码哈希 |
| `avatar_path` | VARCHAR(255) | 是 | NULL | 头像在文件存储根目录下的相对路径 |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 修改时间 |

用户名唯一：

```sql
UNIQUE KEY uk_user_account_username (username)
```

### 6.2 头像与昵称

V1 不做复杂个人资料编辑，不增加昵称。

允许用户上传 JPG 或 PNG 格式头像；文件保存在运行环境的 `files/avatars/`，数据库只保存相对路径 `avatar_path`，不保存服务器绝对路径。

未上传头像时，前端使用用户名首字作为默认头像。

因此暂不增加：

```text
nickname
```

API 对外返回可访问的 `avatarUrl`，由后端基于相对路径拼接，不直接暴露 `avatar_path`。

### 6.3 密码

数据库只保存 BCrypt Hash，不保存明文密码。

## 7. 内容表 content

### 7.1 字段

| 字段 | 类型 | NULL | 默认 | 说明 |
|---|---|:---:|---|---|
| `id` | BIGINT UNSIGNED | 否 | AUTO_INCREMENT | 内容ID |
| `user_id` | BIGINT UNSIGNED | 否 | - | 所属用户 |
| `content` | TEXT | 否 | - | 正文 |
| `category_code` | VARCHAR(32) | 是 | NULL | 分类编码 |
| `remark` | VARCHAR(1000) | 是 | NULL | 备注 |
| `is_pinned` | TINYINT UNSIGNED | 否 | 0 | 是否置顶 |
| `copy_count` | INT UNSIGNED | 否 | 0 | 累计复制次数 |
| `last_copy_time` | DATETIME | 是 | NULL | 最近成功复制时间 |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 最近编辑时间 |
| `deleted` | TINYINT UNSIGNED | 否 | 0 | 逻辑删除 |

正文产品层最大：

```text
5000 字符
```

### 7.2 V1 明确没有的字段

不设计：

```text
title
source_platform
source_url
```

最新版需求已取消来源平台和原始链接。

### 7.3 remark

备注最大：

```text
1000 字符
```

允许 NULL，并参与关键词搜索。

### 7.4 is_pinned

```text
0 = 未置顶
1 = 已置顶
```

V1 不做置顶自定义排序，因此没有 `pin_sort`。

### 7.5 copy_count / last_copy_time

复制成功时更新：

```sql
UPDATE content
SET copy_count = copy_count + 1,
    last_copy_time = NOW()
WHERE id = ?
  AND user_id = ?
  AND deleted = 0;
```

从未复制：

```text
last_copy_time = NULL
```

### 7.6 deleted

```text
0 = 正常
1 = 已删除
```

删除采用逻辑删除，V1 不提供回收站。

## 8. update_time 规则

`update_time` 表示：

> 内容本身最后一次编辑时间。

以下操作更新：

- 正文
- 分类
- 标签
- 备注

以下操作不更新：

- 复制
- 置顶
- 取消置顶

因此不使用：

```sql
ON UPDATE CURRENT_TIMESTAMP
```

否则复制次数变化也会污染更新时间。

真正编辑内容时由 SQL 显式：

```sql
update_time = NOW()
```

### 9.1 字段

| 字段 | 类型 | NULL | 默认 | 说明 |
|---|---|:---:|---|---|
| `id` | BIGINT UNSIGNED | 否 | AUTO_INCREMENT | 标签ID |
| `user_id` | BIGINT UNSIGNED | 否 | - | 所属用户 |
| `name` | VARCHAR(20) | 否 | - | 标签名称 |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |

标签规则：

```text

单条内容最多 10 个标签
```

V1 没有标签管理页面，因此不增加：

```text

```

### 9.2 标签唯一约束

```sql
UNIQUE KEY uk_tag_user_name (user_id, name)
```

同一用户不能重复创建同名标签，不同用户可以各自拥有相同标签。

## 10. 内容标签关系表 content_tag

| 字段 | 类型 | NULL | 默认 | 说明 |
|---|---|:---:|---|---|
| `content_id` | BIGINT UNSIGNED | 否 | - | 内容ID |
| `tag_id` | BIGINT UNSIGNED | 否 | - | 标签ID |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |

联合主键：

```sql
PRIMARY KEY (content_id, tag_id)
```

确保同一内容不能重复绑定同一个标签。

反向查询索引：

```sql
KEY idx_content_tag_tag (tag_id, content_id)
```

V1 不额外增加自增 id。

## 11. 为什么标签不用 JSON

不采用：

```json
["朋友圈","评论"]
```

直接存入 content。

原因：

V1 需要：

- 标签搜索
- 标签复用
- 标签去重
- 已有标签选择
- 同一用户标签唯一

标准 `tag + content_tag` 更适合。

---

## 12. 是否使用数据库外键

V1 建议：

> 不创建物理 FOREIGN KEY。

关系一致性由单体 Spring Boot Service + 事务保证。

不使用外键不代表不校验关系，Service 必须确保：

- Content 属于当前用户
- Tag 属于当前用户
- Content 和 Tag 属于同一个用户

---

## 13. 用户数据隔离

所有私人内容操作必须同时使用：

```text
id
+
当前登录 user_id
+
deleted = 0
```

详情示例：

```sql
SELECT *
FROM content
WHERE id = #{id}
  AND user_id = #{userId}
  AND deleted = 0
LIMIT 1;
```

禁止仅按 id 查询私人内容。

---

## 14. 新增内容事务

```text
BEGIN
→ INSERT content
→ 对每个 tagName 查询当前用户已有标签
→ 没有则创建 tag
→ INSERT content_tag
→ COMMIT
```

任一步失败：

```text
ROLLBACK
```

新增/编辑接口建议前端传：

```text
tagNames
```

而不是传任意 tagId。

---

## 15. 编辑内容事务

V1 使用简单方案：

```text
BEGIN
→ 校验 Content 属于当前用户
→ UPDATE content，并 update_time = NOW()
→ DELETE 原 content_tag
→ 查询 / 创建新的 Tag
→ 重建 content_tag
→ COMMIT
```

不为了节省少量 SQL 实现复杂标签差异算法。

---

## 16. 删除内容

```sql
UPDATE content
SET deleted = 1
WHERE id = #{id}
  AND user_id = #{userId}
  AND deleted = 0;
```

删除内容时 V1 不物理删除 content_tag。

逻辑删除后的内容会被所有正常查询过滤。

---

## 17. 孤立标签

某标签最后一条关联内容被删除后：

> 标签本身继续保留。

以后用户仍然可以重新使用。

V1 不做孤立标签自动清理。

## 19. 搜索设计

V1 使用：

```text
MySQL LIKE
```

搜索范围：

- 正文
- 备注
- 标签
- 分类

推荐使用 `EXISTS` 查询标签，避免同一 Content 因多个 Tag 产生重复记录：

```sql
SELECT c.*
FROM content c
WHERE c.user_id = #{userId}
  AND c.deleted = 0
  AND (
      c.content LIKE CONCAT('%', #{keyword}, '%')
      OR c.remark LIKE CONCAT('%', #{keyword}, '%')
      OR EXISTS (
          SELECT 1
          FROM content_tag ct
          INNER JOIN tag t ON t.id = ct.tag_id
          WHERE ct.content_id = c.id
            AND t.user_id = #{userId}
            AND t.name LIKE CONCAT('%', #{keyword}, '%')
      )
  )
ORDER BY
    c.is_pinned DESC,
    CASE WHEN c.last_copy_time IS NULL THEN 1 ELSE 0 END ASC,
    c.last_copy_time DESC,
    c.update_time DESC,
    c.id DESC
LIMIT #{offset}, #{pageSize};
```

分类中文名称由后端枚举转换。

例如：

```text
文艺 → LITERARY
```

然后追加：

```sql
OR c.category_code = 'LITERARY'
```

## 20. 为什么正文不建普通索引

V1 搜索形式：

```sql
LIKE '%关键词%'
```

普通 BTree 无法有效解决前置 `%`。

因此不创建：

```text
idx_content_content
```

当前单用户数千至一万条数据规模下 MySQL 足够。

## 23. 分页

统一：

```text

pageSize
```

默认：

```text
pageNum = 1
pageSize = 20
```

最大：

```text
pageSize = 100
```

计算：

```text
offset = (pageNum - 1) * pageSize
```

## 24. 列表标签加载与 N+1

禁止：

```text
查 20 条 Content
→ 循环查询 20 次标签
```

推荐：

```text
第 1 次 SQL：分页查询 Content
第 2 次 SQL：根据当前页 contentIds 批量查询所有 Tag
Java：按 contentId 分组
```

批量查询示例：

```sql
SELECT
    ct.content_id,
    t.id AS tag_id,
    t.name AS tag_name
FROM content_tag ct
INNER JOIN tag t ON t.id = ct.tag_id
WHERE ct.content_id IN (...);
```

- 分类不同

## 30. 完整建表 SQL

### 30.1 user_account

```sql
CREATE TABLE user_account (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    username VARCHAR(50) NOT NULL COMMENT '用户名',
    password_hash VARCHAR(100) NOT NULL COMMENT 'BCrypt密码哈希',
    avatar_path VARCHAR(255) DEFAULT NULL COMMENT '头像相对存储路径',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '修改时间',

    PRIMARY KEY (id),
    UNIQUE KEY uk_user_account_username (username)
) ENGINE=InnoDB
DEFAULT CHARACTER SET=utf8mb4
COLLATE=utf8mb4_0900_ai_ci
COMMENT='用户账号表';
```

### 30.2 content

```sql
CREATE TABLE content (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '内容ID',
    user_id BIGINT UNSIGNED NOT NULL COMMENT '所属用户ID',
    content TEXT NOT NULL COMMENT '正文',
    category_code VARCHAR(32) DEFAULT NULL COMMENT '分类编码',
    remark VARCHAR(1000) DEFAULT NULL COMMENT '备注',
    is_pinned TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '是否置顶：0否 1是',
    copy_count INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '累计复制次数',
    last_copy_time DATETIME DEFAULT NULL COMMENT '最近成功复制时间',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '最近编辑时间',
    deleted TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '逻辑删除：0正常 1删除',

    PRIMARY KEY (id),

    KEY idx_content_user_list (
        user_id,
        deleted,
        is_pinned,
        update_time,
        id
    ),

    KEY idx_content_user_category (
        user_id,
        deleted,
        category_code,
        update_time
    ),

    KEY idx_content_user_last_copy (
        user_id,
        deleted,
        last_copy_time

DEFAULT CHARACTER SET=utf8mb4
COLLATE=utf8mb4_0900_ai_ci
COMMENT='用户内容表';
```

## 33. 数据库验收标准

数据库设计通过前必须确认：

- V1 只有 4 张核心表
- 没有 title
- 没有来源平台
- 没有原始链接
- 分类为最新版 8 个分类
- 分类允许 NULL
- 标签属于用户
- 同用户标签唯一
- 单内容多标签通过 content_tag
- 内容使用逻辑删除
- 复制不修改 update_time
- 置顶不修改 update_time
- 所有私人数据可通过 user_id 隔离
- 搜索覆盖正文、标签、分类、备注
- 没有为未来功能提前建表
- Flyway 能完整初始化 V1 结构

## 35. 最终原则

> 能用字段解决的，不增加表。

> 固定分类使用枚举，不建分类表。

> 自由标签使用关系表，不塞 JSON。

> 所有私人数据必须有 user_id 权限边界。
