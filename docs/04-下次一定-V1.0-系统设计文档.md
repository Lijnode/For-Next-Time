# 1. 文档目标

本文档用于确定“下次一定”V1.0 的整体技术方案，作为后续数据库设计、API 设计、AGENTS.md、项目初始化、PC Web 开发、移动 H5 开发、后端开发和部署的技术基线。

本文档评审通过后，开发阶段不得擅自修改：

- 双前端架构

- 数据隔离方案
- 搜索方案
- 数据库类型
- API 前缀
- V1 中间件边界

如确需调整，应先更新设计文档并重新评审。

# 2. 系统定位

V1.0 是一套：

> PC Web + 移动 H5 两套独立前端，共用同一套后端服务和同一份业务数据的私人内容收藏与检索系统。

系统核心闭环：

```text
注册 / 登录
→ 留下一条内容
→ 长期积累
→ 搜索
→ 找到
→ 复制使用
```

技术设计首要目标：

- 简单
- 稳定
- 清晰
- 易维护
- 易部署
- 易于 Vibe Coding
- 为移动端未来迁移小程序保留合理空间

# 3. V1.0 总体架构

```text
PC Web：Vue 3 + Vite + TypeScript
                │
                │ HTTPS / JSON
                ↓
              Nginx
                │
                │ /api/
                ↓
      Spring Boot 3 + Java 21
                │
              MyBatis
                │
              MySQL 8
                ↑
                │ HTTPS / JSON
```

PC Web 与移动 H5：

- 独立工程

但共同调用：

> 同一套 `/api/v1` 后端接口。

后端禁止为 PC 和 H5 分别复制两套业务逻辑。

# 6. 为什么 PC 与 H5 使用不同 UI 组件库

PC Web 更偏桌面网站，使用：

> Element Plus

适合：

- Select
- Input
- Dialog
- Dropdown
- Form
- 桌面交互

移动 H5 更偏 App / 小程序，使用：

> Vant 4

适合：

- Popup
- ActionSheet
- Cell
- Field
- Toast
- Dialog
- 移动触控

两端虽然使用不同 UI 组件库，但必须遵守同一份《UI 设计规范》。

组件库只是基础能力，不得直接使用默认视觉拼成产品。

---

# 7. 为什么移动 H5 V1 不直接使用小程序框架

最新版需求要求：

> V1.0 暂不单独开发微信小程序。

同时要求移动 H5 在不明显增加 V1 成本的前提下，为未来小程序迁移降低改造成本。

因此 V1 不提前决定：

- 原生微信小程序
- uni-app
- Taro
- 其他跨端方案

V1 仍采用熟悉、稳定的：

```text
Vue 3 + Vite + TypeScript
```

未来真正进入小程序版本时，再单独评审技术路线。

当前通过：

- API 层解耦
- 平台能力适配层
- 业务模型平台无关
- 禁止组件直接依赖浏览器 API

降低迁移成本。

```text

├── feedback.ts
```

## 10.1 clipboard.ts

统一：

```text
copyText()
```

当前 H5 内部使用浏览器 Clipboard API。

页面组件不得直接调用：

```text
navigator.clipboard
```

未来迁移小程序时，只替换平台实现。

## 10.2 storage.ts

统一：

```text
getToken()
setToken()
removeToken()
```

当前 H5 内部可使用 localStorage。

页面和 Store 不直接操作 localStorage。

未来小程序可替换为对应平台存储实现。

## 10.3 feedback.ts

统一封装：

- Toast
- Confirm
- Error Message

业务逻辑只表达成功、失败、确认，不直接绑定浏览器 alert。

# 21. 分层职责

## Controller

负责：

- 接收请求
- 参数校验
- 获取当前用户
- 调用 Service
- 返回统一结果

禁止：

- 写复杂业务
- 直接调用 Mapper
- 手动拼 SQL
- 到处 try/catch

## Service

负责：

- 业务规则
- 用户数据归属
- 事务
- 标签处理
- 内容组装

## Mapper

负责：

- SQL
- CRUD
- 分页查询
- 搜索查询

不承载业务决策。

## Entity

仅对应数据库字段。

不能直接作为所有 API 入参和出参。

## Req / Res

Req：API 请求对象。

Res：API 响应对象。

# 25. 登录认证方案

V1 使用：

> JWT Bearer Token。

流程：

```text
用户名 + 密码
→ 后端校验
→ 签发 JWT
→ 前端保存 Token
→ 后续请求 Header 携带 Token
```

Header：

```http
Authorization: Bearer <token>
```

Token 建议有效期：

```text
7 天
```

V1 不实现 Refresh Token。

---

# 26. JWT 内容

只保存必要信息：

```text
userId
username
issuedAt
expireAt
```

严禁放入：

- 密码
- 用户内容
- 大量业务数据

---

# 27. JWT 后端实现

V1 不引入完整 Spring Security RBAC。

建议：

```text
AuthInterceptor
+
JwtUtil
+
UserContext
```

流程：

```text
请求
→ AuthInterceptor
→ 解析 JWT
→ 得到 userId
→ 放入 UserContext
→ Controller / Service
→ 请求结束清理 UserContext
```

`UserContext` 使用 ThreadLocal 时必须在请求结束后 clear。

# 32. 数据权限

这是系统最重要的安全规则之一。

所有用户业务数据必须属于当前登录用户。

前端禁止传：

```text
userId
```

决定数据归属。

后端始终从：

```text
JWT → UserContext
```

获取当前用户。

# 33. 内容权限 SQL 原则

详情、编辑、删除、置顶、复制等操作必须同时包含：

```sql
id = ?
AND user_id = ?
AND deleted = 0
```

不能只使用：

```sql
WHERE id = ?
```

# 36. 标签

标签属于用户。

关系：

```text
User 1:N Tag
Content N:N Tag
```

同一个用户同名标签只保留一个。

不同用户允许存在相同标签名。

# 37. 新增内容事务

新增：

```text
BEGIN
→ 校验当前用户未保存相同正文
→ INSERT content
→ 查询 / 创建标签
→ INSERT content_tag
→ COMMIT
```

任何一步失败整体回滚。

---

# 38. 编辑内容事务

V1 采用简单策略：

```text
BEGIN
→ 校验内容归属
→ 校验当前用户未保存相同正文（排除当前内容）
→ UPDATE content
→ DELETE 原 content_tag
→ 查询 / 创建新标签
→ INSERT 新 content_tag
→ COMMIT
```

不为了少几条 SQL 编写复杂差异算法。


# 43. 为什么 V1 不使用 Elasticsearch

V1 预计单用户数千至一万条内容，MySQL 足够。

当前没有必要增加：

- ES 服务
- 索引同步
- 运维成本
- 数据一致性问题

未来出现真实性能瓶颈再升级。

---

# 44. 为什么 V1 不使用 AI 搜索

最新版需求明确：

> V1 只做关键词搜索。

所以 V1 不引入：

- Embedding
- 向量数据库
- 大模型 SDK
- RAG

以后 AI 语义搜索进入对应版本时再设计。

# 46. 移动端分页表现

- 滚动加载
- 加载更多

但底层仍使用同一套分页接口。

PC 可根据 UI 使用加载更多或页码形式。

---

# 47. 最近使用

定义：

> 最近成功复制过的内容。

数据库依据：

```text
last_copy_time
```

首页建议查询最近 5 条。

排序：

```text
last_copy_time DESC
```

---

# 48. 复制流程

前端：

```text
用户点击复制
→ 平台 Clipboard Adapter
→ 确认复制成功
→ POST /contents/{id}/copy
→ Toast：就是这句
```

只有实际复制成功后才调用后端记录复制。

---

# 49. 复制计数

后端使用原子更新：

```sql
UPDATE content
SET copy_count = copy_count + 1,
    last_copy_time = NOW()
WHERE id = ?
  AND user_id = ?
  AND deleted = 0
```

禁止：

```text
先查次数
→ Java +1
→ 再 Update
```

---

# 50. update_time 规则

以下操作更新：

- 修改正文
- 修改分类
- 修改标签
- 修改备注

以下操作不更新：

- 复制
- 置顶 / 取消置顶

避免“最近更新”排序被使用行为污染。

```text
is_pinned
```

两种状态：

```text

1 已置顶
```

不设计：

- pin_sort

- 置顶分组

# 52. 删除

用户删除后：

```text
deleted = 1
```

# 53. 未保存内容保护

V1 不建立数据库草稿表。

PC Web：

> 可使用页面离开确认 + 本地临时保存。

移动 H5：

> 通过 `platform/storage.ts` 保存临时输入。

保存成功后清理。

V1 不提供草稿箱。

---

# 54. XSS 防护

用户保存的内容必须按普通文本显示。

Vue 使用：

```text
{{ content }}
```

不得直接：

```text
v-html
```

渲染用户正文。

---

# 55. SQL 注入防护

所有 SQL 使用 MyBatis 参数绑定。

禁止字符串直接拼接用户输入。

错误示例：

```java
"WHERE content LIKE '%" + keyword + "%'
```

---

# 56. 文件与图片

V1 仅支持当前用户上传头像：

- 格式：JPEG、PNG
- 单文件大小：不超过 2MB
- 本地开发：项目根目录 `files/avatars/`
- 生产部署：运行 JAR 的服务器本地 `files/avatars/`
- 数据库：仅保存相对路径，不保存服务器绝对路径

头像通过同源 `/files/**` 静态路径读取。V1 不引入 OSS、COS、MinIO 或独立文件服务。

正文内容仍不支持图片、文件上传或 OCR。

---

# 57. CORS 与域名设计

推荐生产环境分别提供：

```text
PC Web：桌面域名
移动 H5：移动域名
```

例如概念上：

```text
www.example.com
m.example.com
```

两端都通过各自 Nginx：

```text
/api/
```

反向代理到同一个后端。

这样前端请求统一使用：

```text
/api/v1/...
```

避免业务代码写死完整 API 域名。

# 87. 系统设计最终结论

“下次一定”V1.0 最终采用：

```text
PC Web：Vue 3 + Vite + TypeScript + Element Plus
                         │
                         ├──────┐
                         │      │
移动 H5：Vue 3 + Vite + TypeScript + Vant
                         │      │
                         └──┬───┘
                            ↓
                     Spring Boot 3
                       + Java 21
                            ↓
                         MyBatis
                            ↓
                         MySQL 8
```

PC 和 H5：

> 两套独立前端。

后端和数据：

> 只有一套。

移动 H5：

> 当前只负责做好 H5，不提前决定小程序技术栈；通过平台能力适配层和统一 API 降低未来迁移成本。

V1 技术设计始终坚持：

> 能简单解决的问题，不提前复杂化。

所有技术决策最终服务于同一条产品闭环：

```text
先留下
→ 找得到
→ 用得上
```
