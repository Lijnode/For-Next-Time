---

# 1. 文档目的

本文档用于统一“下次一定”V1.0 的视觉设计语言和组件表现，作为后续 PC Web、移动 H5、前端组件开发、页面验收、Vibe Coding 和后续小程序迁移的视觉与交互基线。

本文档重点解决：页面看起来应该是什么样、同一类组件应该如何保持一致、PC Web 与移动 H5 应如何分别适配各自设备特征。

本文档不负责数据库结构、API 协议、登录鉴权实现、搜索 SQL、后端模块设计和部署方案，这些内容在后续系统设计文档中确定。

---

# 2. UI 总体定位

“下次一定”不是企业后台、知识库、笔记管理系统、社区内容平台或 AI 写作工具。

它更接近：

> 一个轻量、私人、随时能打开、随时能留一句、需要时马上能找到并复制的内容工具。

整体视觉应传达：年轻、简洁、轻松、克制、有一点温度、有一点互联网语感，但不过度可爱、不过度文艺、不过度科技。

# 4. 视觉原则

## 4.1 正文永远是视觉主体

用户真正关心的是：

> 我以前留下的那句话是什么。

因此所有内容页面中，正文权重最高，标签、分类、时间、统计信息和操作按钮都必须低于正文。

## 4.2 搜索入口必须明显

搜索是“下次一定”的第一优先级能力，因此 PC Web 首页必须让搜索成为明显主入口，移动 H5 首页首屏必须直接看到搜索框，搜索页不能因为装饰元素降低输入效率。

## 4.3 新增必须轻

“先留一句”不能设计成复杂表单。

视觉顺序：

```text
正文
↓
分类
↓
标签
↓
更多信息（备注）
↓
保存
```

正文是唯一核心必填项。

## 4.4 双端视觉统一，布局独立

PC Web 与移动 H5 不是一套前端，也不是简单响应式缩放，两端分别设计。

必须统一：品牌色、字体原则、核心文案、内容卡片气质、按钮状态、标签风格、空状态语气、成功/错误反馈语气和品牌识别。

允许不同：导航结构、页面宽度、卡片列数、交互入口位置、弹层形态、表单排版、Hover、Bottom Sheet 和页面转场。

# 12. 字体

V1.0 不额外引入 WebFont。

中文优先使用系统字体：

```css
font-family:
  -apple-system,
  BlinkMacSystemFont,
  "Segoe UI",
  "PingFang SC",
  "Microsoft YaHei",
  Arial,
  sans-serif;
```

原因：中文显示稳定、加载快、移动端自然、后续小程序迁移成本低，并且不增加字体版权问题。

---

# 13. 字重

推荐只使用：

```text
400 Regular
500 Medium
600 Semibold
700 Bold
```

原则：正文以 400/500 为主，模块标题使用 600，页面标题使用 600/700，不大量使用 800/900 超粗字体。

产品整体应显得轻，而不是“喊”。

# 20. 阴影

整体原则：有层次，但不要“浮起来一大截”。

普通卡片：

```css

```

浮层：

```css
box-shadow: 0 12px 40px rgba(20, 24, 24, 0.10);
```

移动底部导航：

```css
box-shadow: 0 -4px 24px rgba(20, 24, 24, 0.06);
```

禁止黑色重阴影、大范围发光和多层复杂阴影。

# 25. PC 顶部导航

当前确认的 PC UI 不使用全局顶部导航。首页首屏直接承载搜索、筛选和内容浏览，避免将同一搜索能力拆成重复页面；右上角仅保留“先留一句”和用户入口两个轻量操作。

本节下方旧导航规范仅保留历史参考，不再作为 PC Web 验收标准。

PC Web 使用顶部导航。

高度建议：

```text
64～72px
```

结构：

```text
Logo / 品牌
首页
搜索
先留一句
用户入口
```

可根据最终首页布局，将搜索框直接放入导航或首屏主体，但页面中必须始终存在明显搜索入口。

# 27. PC 导航状态

当前确认的 PC 首页在输入关键词后，内容卡片区域原地切换为搜索结果，最近使用区域隐藏；清空关键词或点击“返回全部”后恢复普通内容列表。

当前页面：一级文字、Medium/Semibold，可配轻量底线或浅色背景。

非当前：二级文字。

Hover：文字加深、浅背景、150～200ms 动效。

适用于：删除确认、重要确认。

宽度建议：

```text
360～440px
```

不用于保存成功、复制成功和普通提示。

---

# 49. 移动确认弹层

移动端删除确认可使用 Bottom Sheet Confirm 或系统感 Modal，二选一。

关键要求：操作简单、危险按钮明确、取消更容易。

---

# 50. Toast

统一用于：保存成功、复制成功、置顶成功和普通错误。

PC 推荐统一放页面顶部中间或底部中间，正式实现时选定一种后全局统一。

移动位置：底部导航上方，不遮住输入框、主按钮和 Home Indicator。

普通成功持续 1.5～2 秒，错误持续 2～3 秒。

---

# 51. 品牌文案规范

新增：

> 先留一句

搜索：

> 找找现在用得上的。

保存成功：

> 先留着，下次一定。

复制成功：

> 就是这句。

搜索无结果：

> 这次没翻到合适的。

无内容：

> 这里还空着，先留下一句。

辅助：

> 下次遇见喜欢的，先留在这里。

---

# 52. 文案语气

允许：轻松、简短、有一点“这次/下次”的品牌记忆。

禁止：网络烂梗堆砌、过度卖萌、过度 emo、过度文艺、企业系统语言、“操作成功！”、“数据为空，请新增数据！”。

---

# 53. 空状态

## 53.1 首页无内容

主：

> 这里还空着，先留下一句。

辅：

> 下次遇见喜欢的，先留在这里。

操作：

> 留下第一句

## 53.2 搜索为空

主：

> 这次没翻到合适的。

操作：

> 先留一句

## 53.3 最近使用为空

> 最近还没用上这里的内容。

---

# 54. Skeleton

用于：首页、搜索结果、详情页。

样式应与实际内容结构一致、浅灰、低动效。

不要使用全屏大 Loading 阻断页面。

---

# 55. Loading

按钮提交时：

```text
保存
→ 保存中
```

按钮进入 Loading 后禁止重复点击，但不能立即清空表单。

---

# 56. 网络错误

文案：

> 网络开小差了，请重试。

按钮：

> 重试

不要直接暴露 Request Failed 500 等技术信息。

---

# 57. 图标体系

V1 推荐统一采用 Lucide Icons。

原因：线性简洁、风格现代、PC/H5 都适用、图标数量足够、后续跨端替换成本低。

---

# 58. 图标风格

统一：线性、圆润、1.5～2px Stroke、不使用多色图标。

---

# 59. 禁止混用 Emoji 作为核心图标

正式 UI 中 Home、Search、Plus、User、Copy、Pin、Edit、Delete 必须使用统一图标体系。

Emoji 可以存在于用户保存的正文内容，但不能作为正式导航图标。

---

# 60. 动效

整体：轻、快、克制。

推荐：

```text
150～250ms
```

---

# 61. PC Hover

PC 可使用 Hover。

卡片：轻微 translateY(-1px)，阴影略增强。

按钮：背景或文字轻微加深。

禁止大幅上浮、缩放 1.1 或炫光。

---

# 62. 移动按压

移动使用 Pressed 反馈：轻微透明度变化或背景变化。

不依赖 Hover。

---

# 63. 页面转场

移动 H5 可使用轻微页面进入：opacity + translateY 4～8px，时长 150～200ms。

不使用复杂左右滑屏动画作为强制规范。

---

# 64. PC Web 首页视觉重点

必须形成以下层级：

```text
品牌
↓
搜索
↓
分类
↓
最近使用
↓
全部内容
```

不能让“最近使用”比搜索更抢眼。

---

# 65. 移动首页视觉重点

首屏优先：

```text
品牌
↓
搜索
↓
分类
↓
最近内容
```

底部始终可触达：

```text
＋
```

---

# 66. PC Web 卡片布局

1440px 基准推荐 3 列，较窄桌面 2 列。

卡片宽度优先保证正文舒适阅读。

---

# 67. 移动 H5 卡片布局

始终 1 列。

除特殊信息小组件外，不做双列内容卡片。

---

# 68. PC 新增页

推荐居中窄内容编辑区。

最大宽度：

```text
760～860px
```

避免表单铺满 1440px。

---

# 69. 移动新增页

页面主要区域必须是正文输入框。

保存按钮建议放页面底部明显位置或随内容自然布局，但必须保证单手可触达。

---

# 70. 内容详情

详情正文必须比分类、时间、复制次数字号更大。

PC 详情正文建议 22～26px，移动 20～22px。

---

# 71. 删除按钮位置

删除是最低频、高风险操作。

不得放在卡片主操作区，不得与复制并列同视觉权重，不得使用品牌色。

详情页中应处于低视觉层级。

---

# 72. 可访问性

至少满足：

- 正文和背景对比明显
- 操作不能只靠颜色判断
- 输入框有 Label
- 图标按钮有 aria-label/title
- PC 支持键盘 Tab
- Focus 状态明显
- 移动点击区 >= 44px
- 文字不小到难以阅读

---

# 73. 键盘操作

PC Web：Tab 可遍历主要表单，Enter 可提交常规输入，Esc 可关闭普通 Modal/Popover，搜索输入框 Enter 可触发搜索。

后续可以考虑 Ctrl/Cmd + K 聚焦搜索，但不作为 V1 强制要求。

---

# 74. 内容复制反馈

成功 Toast：

> 就是这句。

不需要大动画、彩纸、Modal 或完成页面。

目标：复制以后立即离开都没问题。

---

# 75. 未保存内容提示

如果用户已有输入并离开：

PC 可使用 Confirm Modal，移动可使用 Bottom Sheet / Confirm。

文案：

> 这句还没留下，确定离开吗？

操作：

```text
继续编辑
直接离开
```

---

# 76. 小程序迁移视觉约束

移动 H5 的 UI 不直接照搬浏览器特性。

避免：浏览器式顶部地址栏设计、右键菜单、Hover 才出现核心按钮、依赖网页固定窗口宽度、依赖浏览器原生 Alert 作为主要交互。

---

# 77. 平台能力视觉解耦

以下行为应定义为产品行为：

```text
复制
Toast
确认
返回
本地登录态
```

而不是在 UI 文档中绑定 navigator.clipboard、localStorage、window.confirm 等具体 Web API。

这样未来迁移小程序时，只需要替换平台实现。

---

# 79. 移动 H5 组件建议

# 80. 双端组件关系

两套前端不要求共用同一套 Vue 组件源码。

但相同业务组件必须遵循同一语义。

例如 PC 与移动都可以分别实现 ContentCard，但都必须表达：正文、标签、置顶、时间和复制。

# 82. 两端 Token 一致性

PC 和移动建议保持一致：Brand Color、Text Color、Border Color、Surface Color、Danger Color、Tag Color。

可以不同：页面最大宽度、卡片内边距、字号细节、导航高度、Bottom Sheet Token、Hover Token。

---

# 83. 禁止页面硬编码

正式开发中禁止在几十个页面重复硬编码颜色值。

应统一通过 Design Token / CSS Variables 管理。

---

# 84. 设计禁止项

V1 UI 明确禁止：

- 企业后台左侧菜单
- 大量 Table
- 大面积渐变
- 霓虹科技风
- 毛玻璃滥用
- 每张卡片一个颜色
- 多套图标混用
- Emoji 当核心导航图标
- 大量深阴影
- 复杂 3D
- 大型数据统计首页
- 分类宫格占满首屏
- AI 推荐区
- 热门榜单
- 社区 Feed
- 公开用户头像流

---

# 85. 业务禁止项

UI 不得擅自新增：

- 来源平台
- 原始链接
- AI 功能
- OCR
- 图片上传
- 收藏
- 星标
- 二次收藏
- 搜索历史
- 社区
- 评论
- 点赞
- 关注
- 标签管理中心
- 分类管理后台
- 数据导入导出入口

这些均不属于 V1.0。

---

# 86. 产品文案禁止项

不得把“先留一句”改成“新增文案”作为主要用户文案。

不得把“这次没翻到合适的。”改成“暂无搜索结果”作为主要空状态。

不得把“就是这句。”改成“复制成功！”作为主要成功反馈。

开发内部字段可以使用标准技术名，但用户界面应遵循品牌语言。

---

# 87. PC Web 验收标准

PC UI 验收时必须确认：

- 是完整桌面网站布局
- 不像手机页面放大
- 不使用移动底部导航
- 搜索足够突出
- 1440px 下横向空间利用合理
- 卡片 2～3 列自然
- 鼠标 Hover 自然
- 详情阅读宽度舒适
- 新增页不是后台表单
- 正文是核心视觉主体

---

# 88. 移动 H5 验收标准

移动 UI 验收时必须确认：

- 像轻量 App / 小程序
- 单列内容
- 底部导航清楚
- 中间新增入口明显
- 搜索首屏可见
- 所有核心触控区 >= 44px
- 不依赖 Hover
- Bottom Sheet 使用自然
- 输入框不会导致浏览器异常缩放
- iPhone Safe Area 正常
- 页面层级不过深
- 为后续小程序迁移保留空间

---

# 89. 双端一致性验收

必须确认同一业务状态在两端具有相同含义。

例如：

```text
PC 已置顶 = 移动已置顶
```

```text
PC 复制一次 = 移动看到 copyCount 已增加
```

```text
移动标签“#开心” = PC 同样显示“#开心”
```

视觉可以不同，业务语义不能不同。

---

# 90. 核心页面 UI 优先级

设计资源优先顺序：

```text
首页
↓
搜索页
↓
新增页
↓
内容卡片
↓
详情页
↓
我的
↓
登录 / 注册
```

原因：前三项直接决定核心产品体验。

---

# 91. 核心设计判断标准

每次 UI 评审都问：

1. 用户能不能第一眼看到搜索？
2. 用户想留一句时，新增是不是足够快？
3. 用户看到内容时，正文是不是最显眼？
4. 用户找到内容后，复制是不是一步完成？
5. 有没有某个元素只是为了“看起来丰富”而存在？

如果有，应优先删除。

---

# 92. 最终 UI 原则

> PC Web 要像一个真正的网站。

> 移动 H5 要像一个轻量 App / 小程序。

> 两端独立设计，但保持同一品牌语言。

> 正文比分类重要。

> 搜索比整理重要。

> 快速保存比字段完整重要。

> 一键复制比复杂详情重要。

> UI 不负责“堆功能”，只负责让用户更快完成“留下、找到、用上”。

---

# 93. 后续约束

本 UI 规范评审通过后，后续系统设计、前端开发和 Vibe Coding 不得擅自：

- 更换主色
- 改变品牌文案
- 改变 PC / 移动双端策略
- 增加来源平台和原始链接
- 引入 V1 范围外模块
- 将 PC Web 与移动 H5 合并为一套响应式业务页面
- 将移动端改造成传统桌面网页缩小版

如确需调整：

> 先修改设计文档并重新评审，再进入开发。
