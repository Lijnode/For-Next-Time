> Slogan：这次先留着，下次一定用得上。 / Next Time, For Sure

> 文档状态：原型设计评审稿  
> 需求依据：《下次一定 V1.0 产品需求文档》

---

## 1. 文档目的

本文档用于在正式 UI 视觉规范和前端开发之前，明确“下次一定”V1.0 的：

- 页面范围
- 页面信息架构
- PC Web 页面结构
- 移动 H5 页面结构
- 核心组件位置
- 页面跳转关系
- 关键交互
- 双端差异
- 双端一致性要求
- 空状态
- 异常状态
- 原型验收标准

本文档重点解决：

> 页面应该怎么组织、用户应该怎么操作。

本文档暂不决定：

- 最终品牌色
- 最终字体
- 精确字号
- 精确圆角
- 精确阴影
- 最终图标库
- 完整 CSS Token
- 最终动画参数

以上内容在后续《UI 设计规范》中正式确定。

# 2. 原型设计原则

## 2.1 两套前端，两套页面设计

V1.0 明确采用：

```text
PC Web
+
移动 H5
```

两端：

- 独立设计
- 独立前端工程实现
- 页面布局不要求一致
- 导航方式不要求一致
- 交互入口位置可以不同

但必须共用：

- 同一套后端接口
- 同一套账号体系
- 同一份内容数据
- 同一套业务规则
- 同一套分类
- 同一套标签
- 同一套搜索规则
- 同一套权限规则

PC Web 不能是移动页面的简单放大版。

移动 H5 也不能是桌面网站的简单压缩版。

---

## 2.2 移动场景优先

虽然 V1.0 同时开发 PC Web 和移动 H5，但移动端仍是最高频使用场景。

移动端核心链路必须优先保证：

```text
看到一句话
→ 打开移动 H5
→ 先留一句
→ 粘贴
→ 保存
```

以及：

```text
需要一句话
→ 打开移动 H5
→ 搜索
→ 找到
→ 复制
```

尽量减少：

- 页面跳转
- 表单字段
- 弹窗
- 二次操作
- 无意义确认

---

## 2.3 搜索优先

“下次一定”最重要的不是展示用户存了多少内容，而是：

> 需要的时候能不能找到。

因此：

- PC Web 搜索入口必须明显
- 移动 H5 首页搜索入口必须处于首屏核心位置
- 搜索结果必须可以直接复制
- 搜索不要求进入详情页才能使用

---

## 2.4 内容优先

页面视觉信息层级必须围绕：

> 正文内容

展开。

不得让：

- 分类
- 标签
- 时间
- 统计数字
- 按钮
- 装饰元素

抢过正文。

---

## 2.5 保存优先简单

新增页面默认只展示：

- 正文
- 分类
- 标签
- 保存

备注放到：

> 更多信息

中。

正文是唯一核心必填项。

---

# 3. 原型设计基准尺寸

## 3.1 PC Web

主要设计基准：

```text
1440 × 900
```

同时考虑常见桌面宽度：

```text
1280
1366
1440
1920
```

PC 原型不要求无限铺满宽屏。

核心内容区域应控制合理最大宽度。

---

## 3.2 移动 H5

主要设计基准：

```text
390 × 844
```

同时考虑：

```text
360px
375px
390px
414px
430px
```

宽度。

移动 H5 不依赖 hover、右键、鼠标悬停等桌面能力完成核心操作。

---

PC Web 和移动 H5 核心业务页面保持一致。

# 5. 全局导航结构

## 5.1 PC Web

当前确认的 PC 信息架构：不使用全局顶部导航，也不提供独立搜索页。

首页作为唯一内容浏览与搜索工作台。关键词输入、分类筛选、搜索结果、复制和分页均在首页完成；清空关键词后恢复普通内容列表。首页右上角仅保留“先留一句”和用户入口两个轻量操作。

本节下方原有的顶部导航示意仅保留历史参考，不再作为 PC Web 验收标准。

PC Web 使用桌面网站式顶部导航。

推荐结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 下次一定        首页       [ 搜索 ]       先留一句       头像 │
└──────────────────────────────────────────────────────────────┘
```

顶部导航核心元素：

- Logo / 产品名
- 首页入口
- 搜索入口或搜索框
- 新增入口
- 用户入口

不使用：

- 移动端底部导航
- 后台系统左侧菜单
- 复杂面包屑作为主要导航

---

## 5.2 移动 H5

移动 H5 使用 App / 小程序式底部导航。

```text
┌──────────────────┐
│                  │
│      页面内容     │
│                  │
│                  │
├──────────────────┤
│ 首页    历史    我的 │
└──────────────────┘
```

“先留一句”固定为页面右下角的悬浮按钮，位于底部导航上方；导航本身采用与屏幕边缘保留间距的浮动容器。

中间：

> ＋

作为新增内容最高频入口。

底部导航只保留：

```text
首页
＋
我的
```

搜索不单独占一个 Tab。

## 8.5 PC 最近使用

首页单独展示最近使用区域。

建议：

- 宽屏位于“全部内容”右侧，作为辅助快速取用栏；中窄屏再放在主内容之后
- 首次加载 10 条无卡片背景的排行榜式列表项；列表固定为约展示 3 条内容的高度并支持纵向滚动，接近底部时追加加载下一批 10 条
- 列表按最近使用顺序显示连续编号，并展示相对使用时间、两行正文摘要和复制操作
- 每条使用单条中性分隔线区分；编号、正文和“时间 · 使用次数”紧凑排布，不复用“全部内容”的完整内容卡片

定义：

> 最近成功复制过的内容。

---

## 8.6 PC 全部内容

PC 应充分利用横向空间。

建议使用：

```text
2～3 列卡片网格
```

具体列数根据可用宽度决定。

不采用传统后台 Table。

标题右侧提供排序切换按钮，点击后在「按时间（默认）」与「按热度」之间直接切换。

排序仅作用于 PC 普通列表和分类筛选列表；搜索结果继续使用既定搜索排序。

卡片宽度接近页面内容区全宽。

一屏应能自然看到：

- 一条完整短内容
- 下一条内容的一部分或完整卡片

避免卡片过高。

# 10. 内容卡片设计

内容卡片是双端最核心的公共业务组件概念。

两端样式不要求完全一致，但展示信息保持一致。

---

## 10.1 必须展示

- 正文
- 0～3 个标签
- 置顶状态（如有）
- 时间或最近使用信息
- 复制操作

---

## 10.2 不直接展示

- 完整备注
- 所有标签
- 创建时间和修改时间同时堆叠
- 大量统计数字

这些信息进入详情页。

---

## 10.3 正文

短内容：

> 完整显示。

较长内容：

> 约 4～6 行后截断。

点击正文区域或卡片主体：

> 进入详情。

---

## 10.4 标签

示例：

```text
#朋友圈
#评论
#开心
```

卡片最多直接展示：

```text
2～3 个
```

多余标签可使用：

```text
+2
```

表示。

---

## 10.5 复制

卡片必须直接提供：

> 复制

成功：

> 就是这句

用户不需要先打开详情页。

---

# 12. P05 新增内容页

## 12.1 核心目标

用户打开页面后：

> 尽可能立即粘贴并保存。

---

│        ┌────────────────────────────────────┐              │
│        │ 粘贴你想以后再用的内容……           │              │
│        │                                    │              │
│        │                                    │              │
│        └────────────────────────────────────┘              │
│                                                            │
│        分类                                                │
│        [ 请选择 / 不分类                      ]            │

# 31. 移动 H5 小程序迁移约束

移动 H5 V1.0 虽然不是小程序，但原型设计阶段应避免强绑定浏览器形态。

---

## 31.1 不依赖浏览器特有导航

核心页面操作不能依赖：

- 浏览器地址栏
- 浏览器工具栏
- 右键
- Hover
- 新窗口

---

## 31.2 平台能力与核心业务分离

以下能力未来可能在小程序中使用不同 API：

- 剪贴板
- 登录态本地保存
- 页面返回
- Toast
- Confirm

因此在产品交互上：

> 明确行为，不绑定具体 Web API 表现。

---

## 31.3 页面结构适合迁移

移动端尽量保持：

- 单页职责清晰
- 路径简单
- 底部主导航简单
- 表单字段平台无关
- 后端接口完全共用

使未来迁移时主要改：

> 页面层 + 平台适配层。

---

# 32. 页面跳转关系

完整业务关系：

```text
登录
├── 注册
└── 登录成功
      ↓
     首页
      ├── 搜索 → 搜索结果
      ├── 先留一句 → 新增内容
      ├── 内容卡片 → 内容详情
      │                ├── 编辑
      │                ├── 置顶
      │                ├── 复制
      │                └── 删除
      │
      └── 我的
           ├── 修改密码
           ├── 关于下次一定
           └── 退出登录
```

移动 H5：

```text
首页 ←→ ＋新增 ←→ 我的
```

通过底部导航连接主要入口。

---

# 33. PC Web 页面重点

PC Web 原型必须体现以下特征：

1. 像完整内容网站，而不是 App 放大。
2. 搜索入口更突出。
3. 横向空间利用合理。
4. 内容列表允许 2～3 列。
5. 鼠标操作自然。
6. 顶部导航自然。
7. 页面不采用传统后台 Table。
8. 页面最大宽度受控。
9. 不出现移动底部导航。
10. 详情和编辑页面保持舒适阅读宽度。

---

# 34. 移动 H5 页面重点

移动 H5 原型必须体现：

1. App / 小程序式页面节奏。
2. 单列内容。
3. 底部导航。
4. 中间明显新增入口。
5. 搜索在首页首屏。
6. 主要按钮适合单手操作。
7. 不依赖 Hover。
8. 尽量减少多层级页面。
9. 弹层符合移动习惯。
10. 为未来小程序迁移保留空间。

---

- 热门榜单
- 社区
- 点赞
- 收藏
- 星标
- 数据统计中心
- 搜索历史

- 内容分享
- 公开主页
- 用户关注
- 复杂分类管理
- 标签管理中心
- 来源平台
- 原始链接

# 38. 原型评审重点

原型完成后重点评审：

### 38.1 PC 首页

- 是否像完整网站？
- 搜索是否足够突出？
- 是否充分利用宽屏？
- 卡片密度是否合适？
- 是否存在移动页面放大的感觉？

### 38.2 移动首页

- 是否像 App / 小程序？
- 单手操作是否自然？
- 新增入口是否足够明显？
- 搜索是否能快速触达？
- 卡片是否过高？

### 38.3 新增

- 是否能做到“粘贴即可保存”？
- 分类和标签是否阻碍保存？
- 备注是否足够弱化？

### 38.4 搜索

- 输入和结果是否在一个连续操作链路中？
- 是否可以直接复制？
- 空结果是否自然引导新增？

### 38.5 内容详情

- 正文是否仍然是视觉主角？
- 复制是否优先？
- 删除是否足够弱化且安全？

---

# 39. 原型通过标准

只有同时满足以下条件，原型才能进入下一阶段：

- PC Web 和移动 H5 均完成核心页面设计
- 两端不是简单缩放关系
- 两端核心业务能力一致
- 首页搜索入口突出
- 新增流程足够短
- 搜索结果可以直接复制
- 正文是内容卡片的视觉主体
- 来源平台和原始链接未重新加入
- 分类与最新版需求一致
- 产品文案与最新版需求一致
- 移动 H5 不依赖桌面交互
- 移动 H5 具备未来小程序迁移的基础
- 没有擅自增加 V1.0 范围之外功能

---

# 40. 最终原型原则

> PC Web 要像网站。

> 移动 H5 要像 App / 小程序。

> 两端页面可以不同，但业务不能不同。

> 搜索永远比整理重要。

> 正文永远比标签和统计重要。

> 新增永远不能因为表单过重而变慢。

> 找到以后，应该马上就能复制。

> 当前版本只解决“先留下，之后找得到、用得上”。
