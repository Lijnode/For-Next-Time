> 文档版本：V1.0  
> 产品版本：V1.0 MVP  
> 产品名称：下次一定 / For Next Time  
> API 前缀：`/api/v1`  
> 文档状态：API 设计评审稿  
> 设计依据：《下次一定 V1.0 产品需求文档》《下次一定 V1.0 系统设计文档》《下次一定 V1.0 数据库设计文档》

---

# 1. 文档目标

本文档用于统一 V1.0：

- PC Web
- 移动 H5
- Spring Boot 后端

之间的接口协议。

V1.0 两套前端必须：

> 共用同一套 API。

禁止出现：

```text
/api/v1/pc/...
/api/v1/h5/...
```

两套重复业务接口。

本文档通过评审后，前后端开发必须以此文档为准。

---

# 2. API 基础路径

统一：

```text
/api/v1
```

示例：

```http
POST /api/v1/auth/login
GET  /api/v1/contents
```

健康检查例外：

```http
GET /api/health
```

健康检查不属于业务 API 版本路径。

---

# 3. 请求格式

业务请求默认：

```http
Content-Type: application/json
```

头像上传接口 `POST /api/v1/user/avatar` 例外，使用：

```http
Content-Type: multipart/form-data
```

除头像上传外，V1.0 没有：

- 文件上传
- 图片上传
- multipart/form-data

---

# 4. 响应格式

业务接口统一返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

Java 建议：

```text
Result<T>
```

字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | Integer | 业务码 |
| `message` | String | 提示信息 |
| `data` | T | 业务数据 |

---

# 5. 成功响应

统一：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

如果接口没有业务数据：

```json
{
  "code": 0,
  "message": "success",
  "data": null
}
```

不得因为接口没有返回值而设计另一套响应格式。

---

# 6. 分页响应

分页统一：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "pageNum": 1,
    "pageSize": 20,
    "total": 128,
    "pages": 7,
    "list": []
  }
}
```

Java：

```text
PageResult<T>
```

字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `pageNum` | Integer | 当前页 |
| `pageSize` | Integer | 每页数量 |
| `total` | Long | 总记录数 |
| `pages` | Integer | 总页数 |
| `list` | List<T> | 当前页数据 |

空分页：

```json
{
  "pageNum": 1,
  "pageSize": 20,
  "total": 0,
  "pages": 0,
  "list": []
}
```

数组字段为空时返回：

```json
[]
```

不得返回：

```json
null
```

---

# 7. 分页参数

统一：

```text
pageNum
pageSize
```

默认：

```text
pageNum = 1
pageSize = 20
```

限制：

```text
pageNum >= 1
1 <= pageSize <= 100
```

后端：

```text
offset = (pageNum - 1) * pageSize
```

# 8. HTTP 状态码

业务码和 HTTP 状态码同时使用。

| HTTP | 场景 |
|---|---|
| `200` | 业务成功 |
| `400` | 请求参数 / 请求格式错误 |
| `401` | 未登录、Token 无效、Token 过期 |
| `403` | 已登录但禁止执行某操作 |
| `404` | 资源不存在 |
| `500` | 系统异常 |

对于私人内容：

> “不存在”和“不是当前用户的数据”统一按内容不可用处理，避免泄露其他用户资源是否存在。

# 14. V1.0 没有后端退出登录接口

V1 JWT 为：

> 无状态 Token。

因此不设计：

```text
POST /api/v1/auth/logout
```

退出登录由前端完成：

```text
清除本地 Token
→ 清除用户状态
→ 跳转登录页
```

因为 V1 不使用：

- Redis Session
- Token 黑名单
- Refresh Token
- Session 表

所以后端没有必要提供一个“什么都不做”的 logout API。

# 15. 注册

```http
POST /api/v1/auth/register
```

无需登录。

---

## 15.1 请求

```json
{
  "username": "xiaohzi",
  "password": "12345678",
  "confirmPassword": "12345678"
}
```

---

## 15.2 参数

### username

规则：

```text
必填
trim 后不能为空
3～50 字符
```

V1 不额外限制只能使用：

- 英文字母
- 数字
- 下划线

除非后续需求文档明确增加该规则。

---

### password

```text
必填
8～64 字符
```

---

### confirmPassword

```text
必填
必须与 password 一致
```

---

## 15.3 注册流程

```text
校验参数
→ 查询 username 是否存在
→ BCrypt 加密密码
→ INSERT user_account
→ 签发 JWT
→ 返回登录信息
```

需求要求：

> 注册成功后自动登录。

因此注册成功直接返回 Token。

---

## 15.4 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "token": "eyJhbGciOi...",
    "tokenType": "Bearer",
    "expiresIn": 604800,
    "user": {
      "id": 1,
      "username": "xiaohzi"
    }
  }
}
```

`expiresIn`：

```text
单位：秒
7 天 = 604800
```

---

## 15.5 用户名重复

```json
{
  "code": 10001,
  "message": "用户名已存在",
  "data": null
}
```

## 17.2 contentCount

定义：

# 20. categoryCode

可选。

合法值：

```text
FUNNY
ABSTRACT
EMOTION
LITERARY
HEALING
SOBER
SARCASM
OTHER
```

中文：

```text
FUNNY      搞笑
ABSTRACT   抽象
EMOTION    感情
LITERARY   文艺
HEALING    治愈
SOBER      清醒
SARCASM    阴阳
OTHER      其他
```

不分类：

```json
"categoryCode": null
```

---

# 21. tagNames

新增 / 编辑统一直接传标签名称：

```json
"tagNames": [
  "朋友圈",
  "评论"
]
```

而不是：

```json
"tagIds": [1, 2]
```

原因：

- 用户可以直接新建标签
- 后端可以自动复用已有标签
- 减少前端接口调用
- 降低用户数据越权风险

---

# 22. tagNames 后端处理规则

后端必须：

```text
trim
→ 删除空字符串
→ 当前请求内去重
→ 校验每个标签 1～20 字符
→ 校验总数 <= 10
```

数据库：

```text
UNIQUE(user_id, name)
```

进一步保证同用户标签唯一。

正确：

# 44. /copy 不更新 updateTime

> 内容编辑。

```text

```

# 45. /copy 响应

```json

  "data": {
    "copyCount": 13,
```

# 46. 剪贴板成功但统计接口失败

可能出现：

```text
文字已经复制成功
→ /copy 因网络问题失败
```

此时用户核心操作：

> 已经成功。

V1 前端不要因为统计接口失败告诉用户“复制失败”。

可以：

- 仍展示复制成功反馈
- 记录统计失败日志
- 不自动无限重试

因为直接重试 `/copy` 存在：

> 重复计数风险。

V1 接受极少量统计误差，不为此引入复杂幂等机制。

没有必要。

```text
→ 绑定
```

复制：

```text
platform/clipboard.copyText()
→ 成功
→ POST /contents/{id}/copy
```

业务接口：

> 与 PC 完全一致。

# 94. API 设计原则

> 两套前端只允许有一套业务 API。

> 用户身份只相信 JWT，不相信前端 userId。

> 新增和编辑使用一致内容模型。

> 内容列表、搜索、最近使用复用同一列表响应模型。

> 用户输入标签名，后端负责标签复用和创建。

> 数据库字段不直接等于 API 字段。

> V1 不为未来功能提前创建接口。

> API 必须保持简单、明确、可调试。

---

# 95. API 验收标准

API 设计通过前必须确认：

- PC 与 H5 共用同一套 API
- 注册成功自动登录
- JWT 有效期明确
- 没有后端 logout 伪接口
- 当前用户接口不返回不存在的 nickname / avatar
- 内容接口没有 title
- 内容接口没有 sourcePlatform
- 内容接口没有 sourceUrl
- 分类使用最新 8 个编码
- tagNames 由后端创建 / 复用标签
- 所有私人内容接口均校验当前 userId
- 搜索覆盖正文、标签、分类、备注
- 最近使用严格以复制成功为定义
- copy 不更新 updateTime
- pin 不更新 updateTime
- 列表 / 搜索使用统一分页结构
- 空数组统一返回 []
- 可选字段无值统一返回 null
- 没有擅自新增 V1 范围外 API
